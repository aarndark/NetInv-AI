# NetInv — инвентаризационное сканирование подсети для Continuous Penetration Test

Комплект скриптов и web-приложения для периодического инвентаризационного
сканирования подсети организации с накоплением истории и выявлением отличий
между запусками. Рассчитан на запуск из **Kali Linux 2026.1** с использованием
предустановленных инструментов (`nmap`, `whatweb`, `curl`).

> Применяйте только в пределах сетей, которыми владеете или на сканирование
> которых имеете письменное разрешение. Инструмент предназначен для легального
> Continuous Penetration Test по своему периметру.

## Что выявляется

Для каждого узла сохраняются и отображаются в таблице:

| Поле | Источник |
|------|----------|
| Дата сканирования | время текущего запуска |
| IP-адрес | nmap |
| Доменное имя | обратный DNS `dig -x <IP> +short` (PTR), иначе hostname из nmap, иначе имя из прямой разведки доменов |
| **Источник** | откуда IP попал в скан: CIDR / домен / поддомен |
| **Описание** | редактируемое поле, хранится в связке с IP (не зависит от запуска) |
| **Администраторы** | редактируемое поле, хранится в связке с IP (в 1.3.0) |
| **Контроль и защита** | галочки CPT / SOC / сканер уязвимостей / WAF / DDOS (в 1.3.0) |
| Открытые порты (с учётом SYN Flood/SYN Cookies) | nmap `-sT`, пометка confidence |
| Опубликованные сервисы | nmap `-sV` + NSE banner |
| Web-ресурсы | curl + whatweb (код ответа, Server, title, технологии) |
| **Уязвимости** | базовая проверка web (curl / nmap-http / nikto / wpscan / dalfox), обоснование severity, блок CVE с CVSS и ссылкой на NVD (в 1.4.0) |
| **Первое обнаружение** | фиксируется один раз на IP (в рамках класса скана) |
| Дата предыдущего сканирования | история запусков |
| Отличия от предыдущего | diff-движок |
| Дата позапрошлого сканирования | история запусков |
| Отличия от позапрошлого | diff-движок |

> Колонка «Описание» редактируется прямо в web-отчёте (сохранение по нажатию
> Enter или потере фокуса, через AJAX) и попадает в CSV. Привязка — к IP, а
> не к конкретному запуску, поэтому описание сохраняется между сканированиями.

## Новое в версии 1.6.2

Восстановлен онлайн-поиск CVE через OSV (api.osv.dev). По результатам
диагностики выявлены и устранены три причины сбоев.

### 1. Онлайн-CVE через AdGuard VPN — только на фазу CVE

Из сети объекта прямой выход к `api.osv.dev` заблокирован (таймаут соединения
и по IPv4, и по IPv6). Доступ появляется только через VPN. Поэтому сканер
**поднимает AdGuard VPN один раз в начале блока онлайн-CVE и гасит его сразу
после** — так основное сканирование подсети (nmap `-sT`) идёт по штатному
маршруту без VPN, а к OSV мы ходим через туннель.

- Механизм: `adguardvpn-cli connect -l <локация>` / `disconnect` (по умолчанию
  через `sudo -n`, если скан запущен не от root).
- Локация по умолчанию — **Helsinki**. VPN поднимается один раз на весь
  проход CVE (reference counting: параллельные сканы из Flask переиспользуют
  один туннель), отключается по завершении последнего.
- **Graceful degradation**: если `adguardvpn-cli` не установлен, нет прав
  `sudo` (не настроен NOPASSWD) или туннель не поднялся — онлайн-CVE
  пропускаются, продолжает работать offline-таблица. Скан не падает.
- VPN гасится в `finally` скана при любом исходе (успех/ошибка/отмена/пауза).

**Переменные окружения:**

| Переменная | По умолчанию | Назначение |
|------------|--------------|------------|
| `NETINV_OSV_VPN` | `1` | Включить авто-VPN на фазу CVE (`0` — выключить) |
| `NETINV_OSV_VPN_LOCATION` | `Helsinki` | Локация выхода AdGuard VPN |
| `NETINV_OSV_VPN_BIN` | `adguardvpn-cli` | Путь к бинарю CLI |
| `NETINV_OSV_VPN_SUDO` | `1` | Запускать CLI через `sudo -n` (`0` — без sudo) |
| `NETINV_HTTPS_PROXY` | — | Если задан — VPN **не** используется, маршрут к OSV обеспечивает оператор (прокси) |

> Настройте `NOPASSWD` для `adguardvpn-cli` в `sudoers` (или запускайте от
> root), иначе поднять VPN в фоне скана не выйдет — сработает деградация.

### 2. Маппинг баннеров nmap → пакет OSV (name + ecosystem)

OSV `/v1/query` требует при идентификации по имени **одновременно**
`package.name` И `package.ecosystem`. Баннеры nmap («Apache httpd»,
«Golang net/http server» и т.п.) — это не имена пакетов OSV. Добавлена
таблица сопоставления: продукт → (`name`, `ecosystem`). Примеры:

| Баннер nmap | OSV name | OSV ecosystem |
|-------------|----------|---------------|
| Apache httpd / apache2 | `apache` | OSS-Fuzz |
| nginx | `nginx` | OSS-Fuzz |
| OpenSSH / ssh | `openssh` | OSS-Fuzz |
| OpenSSL | `openssl` | OSS-Fuzz |
| curl | `curl` | OSS-Fuzz |
| SQLite | `sqlite3` | OSS-Fuzz |
| PostgreSQL | `postgresql` | OSS-Fuzz |
| Golang net/http | `stdlib` | Go |
| Python | `cpython` | OSS-Fuzz |

### 3. Больше никаких HTTP 400 «Invalid query»

Заведомо некорректные запросы **не отправляются**:

- продукт не сопоставлен с экосистемой OSV → онлайн-запрос пропускается
  (используется offline-таблица);
- продукт сопоставлен, но нет версии (для этих пакетов версия обязательна) →
  запрос без версии не шлётся.

Корректный запрос формируется как `{"package": {"name": ..., "ecosystem": ...},
"version": ...}`. Это устранило поток ошибок HTTP 400 в логе.

> Проверить доступность OSV вручную из CLI:
> `adguardvpn-cli connect -l Helsinki` →
> `curl -sS -X POST https://api.osv.dev/v1/query -d '{"version":"1.21.0","package":{"name":"stdlib","ecosystem":"Go"}}'`
> → `adguardvpn-cli disconnect`.

Покрытие тестами — `scanner/test_osv_v162.py` (маппинг, отсечка битых
запросов без обращения к сети, форма payload, graceful degradation без VPN,
идемпотентность teardown).

## Новое в версии 1.6.1

Точечные правки web-интерфейса по итогам эксплуатации: управление активным
сканом, косметика истории и автоматическое разрешение конфликтов IP
в поддоменах.

### Управление активным сканированием (вкладка «Текущее сканирование»)

У каждого активного скана в таблице появилась колонка **«Управление»** с
кнопками:

- **‖ Пауза** — приостановить сканирование. Длинные внешние процессы (nmap)
  замораживаются на уровне ОС сигналом `SIGSTOP` всей группе процессов;
  между этапами сканер сам встаёт на паузу в точке контроля. Статус меняется
  на «приостановлено», кнопка превращается в **▶ Продолжить** (`SIGCONT`).
- **✕ Отменить** — корректно прервать сканирование с подтверждением. Уже
  собранные данные (узлы, порты) сохраняются, запуск помечается статусом
  **«отменено»** (`cancelled`), процесс nmap завершается (`SIGTERM`).

Состояние (выполняется / приостановлено / отменяется) обновляется в реальном
времени по опросу `/current/status` и применяется к строке без перезагрузки
страницы. Механизм кооперативный и graceful: если сигналы недоступны
(не-POSIX), пауза сводится к ожиданию между этапами, а отмена — к остановке
после текущего этапа. Реализация — модуль `scanner/scancontrol.py`
(класс `ScanControl`), маршруты `POST /current/<id>/pause|resume|cancel`.

### Косметика вкладки «История сканирований»

- В колонке **«Статистика»** чип «Palo Alto» переименован в **«артефакты»**
  (учитываются те же узлы — кандидаты на артефакты защиты Palo Alto).
- В колонке **«Ошибки сканирования»** убран вводный раскрывающийся блок
  «о деградации»; остаются только фактические записи об ошибках/деградации
  по модулям.
- Статусы запусков в истории выводятся по-русски: готово / выполняется /
  ошибка / **отменено**.

### Поддомены: автоматическое разрешение конфликтов IP

Раньше при разных IP от разных утилит (например, dnsmap vs dnsrecon) один
и тот же FQDN присутствовал в таблице несколькими строками, а оператору
предлагался ручной resolve. Теперь:

- Каждая пара **домен–IP присутствует в таблице ровно один раз**. После
  каждого скана функция `db.auto_resolve_subdomains()` автоматически схлопывает
  все строки одного FQDN в одну: выбирается **один актуальный IP** — наиболее
  свежий по `last_seen`, при равенстве — подтверждённый бо́льшим числом утилит.
  Ручной выбор оператора (`resolved_ip`), если он был, имеет приоритет.
- Отброшенные IP сохраняются в поле `alt_ips`, все утилиты агрегируются
  в `tools`, а факт авто-разрешения фиксируется флагом `auto_resolved`.
- Из столбцов **«Первое обнаружение»** и **«Последнее обнаружение»** убраны
  метки утилит — остаются только даты.
- Добавлен столбец **«Информация»** со сводкой: число использованных утилит,
  метка «авто-resolve» при разрешённом конфликте и раскрывающийся список
  «подробнее» — полный перечень утилит и описание разрешённого конфликта IP
  (какой IP выбран, какие отброшены).
- В сводке над таблицей вместо «конфликты IP» показывается чип
  **«разрешено конфликтов IP»**.

## Новое в версии 1.6.0

Крупное обновление web-интерфейса: рабочая область разделена на **три вкладки**,
добавлены управление историей, детализация опций и ошибок сканирования,
отдельное окно поддоменов и команды сброса базы в CLI.

### Три вкладки

Верхняя навигация теперь состоит из трёх вкладок:

1. **Объекты сканирования** (стартовая) — список объектов (подсетей/доменов),
   переход к отчёту по каждому. Блок «Последние запуски» с этой страницы
   убран, чтобы стартовый экран оставался обзорным.
2. **Текущее сканирование** — если скан активен, показывается его статус
   (индикатор выполнения, автообновление каждые 5 секунд). Если активного
   скана нет — отображается результат последнего запуска класса `main`
   вместе с блоком поддоменов и сводкой ошибок сканирования. Доступна
   выгрузка CSV.
3. **История сканирований** — полная история с разбивкой по объектам,
   фильтрами (объект / класс / диапазон дат), статистикой по каждому запуску,
   детализацией опций и ошибок, удалением и сравнением.

### Статистика запуска

В строке каждого запуска выводятся чипы: число узлов, живые узлы, узлы за
Palo Alto (SYN Flood/SYN Cookies), открытые порты, число поддоменов (клик →
окно поддоменов) и ссылка на лог-файл запуска.

### Колонка «Опции»

Три раскрывающихся списка по каждому запуску:

- **команда nmap** — фактическая строка запуска nmap;
- **модули** — список применённых модулей с их статусом (использован /
  пропущен: инструмент отсутствует / пропущен: graceful degradation);
- **опции** — все опции расширенного (`advanced`) сканирования.

### Колонка «Ошибки сканирования»

Раскрывающиеся списки ошибок по модулям. В начале блока — пояснение о
принципе **graceful degradation** (отсутствие инструмента или сбой модуля не
прерывает скан). Ошибки помечаются бейджами: `ошибка` (сбой модуля) и
`деградация` (модуль пропущен из-за отсутствия инструмента). **Недоступность
хостов в ошибки не вносится** — это штатный результат сканирования, а не сбой.

### Удаление сканирований

В истории вместо колонки «Команда nmap» — колонка **«Удалить»** (значок
корзины) с подтверждением: «Вы хотите удалить из базы данных результаты
&lt;класс&gt; сканирования от &lt;дата время&gt;». После удаления состояние узлов
(`host_state`) и признаки первого/последнего обнаружения корректно
перестраиваются по оставшимся запускам.

### Сравнение запусков (до 5)

Галочками можно выбрать **до 5** запусков одного объекта. Эталоном становится
**первый** выбранный запуск. Кнопка «Сравнить» открывает таблицу с колонками
«Эталон» и «Отличия от сканирования &lt;дата&gt;» для каждого из остальных:
появившиеся/исчезнувшие IP, добавленные (`+`) и пропавшие (`−`) порты, либо
«без отличий». Доступна выгрузка сравнения в CSV (одного запуска, нескольких
и результата сравнения).

### Окно поддоменов

Отдельное окно показывает поддомены объекта: FQDN, IP, дату первого и
последнего обнаружения с указанием утилиты. Реализованы:

- **конфликты IP** (один FQDN → несколько IP) с выбором актуального адреса
  (`resolve`);
- **привязка** новых поддоменов и **отвязка** исчезнувших — по одному или
  все сразу, с подтверждением;
- **подсветка** новых и исчезнувших поддоменов, легенда.

### CLI: сброс базы

- `netinv -dbreset` — обнуление истории сканирований (запуски, результаты,
  поддомены, ошибки). Пользователи, логи и объекты сканирования сохраняются.
- `netinv -fullreset` — полный откат базы к исходному состоянию. Требует
  авторизации и явного подтверждения.

## Новое в версии 1.5.1

### Исправление: логи не появлялись в `/opt/netinv/logs`

Исправлена ситуация, когда подробные логи сканирований (`netinv_YYMMDD_TIME.log`)
не появлялись в `/opt/netinv/logs`, хотя сканирование проходило.

**Причина.** Если каталог `/opt/netinv/logs` был создан под `root` (например,
при установке через `sudo`), а web/cron NetInv запускались от обычного
пользователя, то записи в него не было. Старый код в этом случае пытался
использовать фолбэк `<корень проекта>/logs`, но при установке в `/opt/netinv`
это **тот же самый недоступный каталог**, поэтому логи «молча» уходили в
`/tmp/netinv_logs`, а пользователь искал их в `/opt/netinv/logs`.

**Что изменено:**

- `resolve_log_dir()` больше не дублирует основной каталог в списке кандидатов
  и **явно объясняет причину** недоступности (владелец, права, текущий
  пользователь) с готовой командой `chown` для исправления.
- При старте каждого скана в консоль и в UI выводится **громкое предупреждение**
  с фактическим путём лога, если сработал фолбэк (строка
  «Каталог логов по умолчанию … недоступен … используется фолбэк: …»).
- Рядом с логом и в `<корень проекта>/logs` пишется файл-указатель
  **`LAST_LOG_PATH`** с абсолютным путём последнего лога — его всегда можно
  посмотреть, даже если лог ушёл в `/tmp`.
- Добавлена команда диагностики **`./netinv logpath`** (она же
  `python scanner/logsetup.py --where-logs`): показывает корень проекта,
  значение `NETINV_LOG_DIR`, доступность основного и фолбэк-каталогов и
  **фактический** путь, куда будут писаться логи, с причиной.
- `install.sh` теперь всегда передаёт владение `/opt/netinv/logs`
  пользователю запуска (`SUDO_USER`), проверяет реальную возможность записи и
  предупреждает, если проект установлен **не** в `/opt/netinv`.

**Быстрая диагностика, если логов нет в `/opt/netinv/logs`:**

```bash
cd /opt/netinv
./netinv logpath            # покажет фактический путь и причину
cat /opt/netinv/logs/LAST_LOG_PATH   # абсолютный путь последнего лога
# типовое исправление прав:
sudo chown -R "$(id -un):$(id -gn)" /opt/netinv/logs
sudo chmod 0775 /opt/netinv/logs
# или жёстко задать каталог логов:
export NETINV_LOG_DIR=/opt/netinv/logs
```

## Новое в версии 1.5.0

### 1. Корректная установка dalfox (go / snap)

`dalfox` (лёгкая проверка XSS) **отсутствует в apt-репозиториях Kali/Debian по
умолчанию**, поэтому установщик (`install.sh`) теперь ставит его отдельной
секцией двумя способами:

1. **Приоритет — `go install`:** `go install github.com/hahwul/dalfox/v2@latest`.
   Если Go не установлен, установщик ставит пакет `golang-go` через apt.
2. **Фолбэк — `snap install`:** `snap install dalfox`. Если `snapd` не
   установлен, установщик ставит `snapd` через apt.

После установки создаётся симлинк `/usr/local/bin/dalfox` — он гарантированно
находится в `PATH` у web/cron-процессов NetInv. Установка зависимостей может
запрашивать права root — **это допустимо**. Любые сбои не прерывают установку:
сканер корректно деградирует без dalfox.

Ручная установка (если нужно):

```bash
go install github.com/hahwul/dalfox/v2@latest     # бинарник в ~/go/bin
sudo ln -sf ~/go/bin/dalfox /usr/local/bin/dalfox  # чтобы был в PATH
# либо:
sudo snap install dalfox
```

### 2. Надёжное обнаружение dalfox (и других не-apt утилит)

Раньше dalfox, успешно отвечающий на `dalfox -h` в интерактивной оболочке,
мог помечаться в NetInv как «недоступный». Причина: `go install` кладёт
бинарник в `~/go/bin` (или `/root/go/bin` под root), которого **нет в `PATH`**
у процесса NetInv — особенно при запуске из web/cron под отдельным пользователем.

Новый модуль `scanner/toolpath.py` ищет утилиты не только в `PATH`, но и в
типовых каталогах установки: `$GOBIN`, `$GOPATH/bin`, `~/go/bin`,
`/root/go/bin`, `/snap/bin`, `/usr/local/bin`, `~/.local/bin`. Эти каталоги
также однократно добавляются в `PATH` процесса, чтобы их видели и дочерние
процессы. Используется в `preflight.py` и `webscan.py` для всех внешних утилит
(curl, whatweb, nikto, wpscan, nmap, dalfox).

### 3. Иерархическая сортировка доменов

Домены и поддомены в отчёте теперь сортируются **иерархически**: родительский
домен идёт первым, сразу за ним — его поддомены (в алфавитном порядке), затем
следующий родительский домен. Например:

```
domaina.ru
alpha.domaina.ru
beta.domaina.ru
delta.domaina.ru
domainb.ru
domainc.ru
```

Реализовано через ключ сортировки `tuple(reversed(labels))` в `db.py` и
`dns_recon.py` (сравниваются метки домена справа налево: зона → домен → поддомен).

Добавлен значок NetInv (спутниковая тарелка + сигнал) в заголовок вкладки

### 5. Проверка доступности OSV при запуске + прокси/VPN

При сканировании в терминал могли сыпаться ошибки онлайн-проверки CVE:

```
[cve] OSV недоступен для X: <urlopen error [Errno 111] Connection refused>
[cve] OSV ... HTTP Error 400: Bad Request
```

**С чем это связано:**

- **`Connection refused` (Errno 111)** — у процесса нет прямого выхода в
  Интернет к `api.osv.dev`: геоблокировки, firewall или корпоративный периметр
  режут egress. Онлайн-CVE при этом пропускаются, работает offline-таблица.
- **`HTTP Error 400: Bad Request`** — OSV не понял запрос. Частая причина —
  передача **пустой** строки версии (`version: ""`) или хвостовые пробелы в
  имени продукта/версии.

**Какой ресурс/софт делает запросы.** Запросы к OSV делает **сам сканер NetInv**
(`scanner/cve_lookup.py` через стандартную библиотеку `urllib`), а не цель
сканирования. Это HTTP POST на `https://api.osv.dev/v1/query`.

**Что исправлено в 1.5.0:**

- **Однократная проверка доступности OSV при запуске скана** (`osv_healthcheck`):
  выполняется один раз за скан, а не на каждый продукт — в терминал больше не
  сыпятся однотипные ошибки. При недоступности печатается понятное пояснение
  причины и подсказка про VPN/прокси.
- **Фикс HTTP 400:** пустая версия больше не отправляется (ключ `version`
  добавляется только при непустом значении), имя продукта и версия очищаются от
  хвостовых пробелов (`strip()`).
- **Поддержка прокси/VPN:** запросы OSV можно направить через HTTP(S)-прокси
  переменной окружения `NETINV_HTTPS_PROXY` (или штатными `HTTPS_PROXY`/
  `https_proxy`). Для VPN прокси не нужен — достаточно поднять туннель до запуска.

**Как проверить доступность OSV вручную:**

```bash
# 1) Доступен ли хост вообще (любой ответ = хост достижим):
curl -I https://api.osv.dev

# 2) Рабочий запрос по версии ПО (корректный payload, не должно быть 400):
curl -X POST https://api.osv.dev/v1/query \
  -H 'Content-Type: application/json' \
  -d '{"version":"2.4.49","package":{"name":"apache"}}'

# 3) Через прокси (если прямой доступ закрыт):
curl -x http://127.0.0.1:8080 -I https://api.osv.dev
```

Запуск NetInv с прокси для OSV:

```bash
export NETINV_HTTPS_PROXY=http://127.0.0.1:8080
./netinv                 # web
./netinv scan --main     # CLI
```

Если все варианты `curl` тоже не проходят — проблема в сети/egress (геоблок,
firewall), а не в NetInv: поднимите VPN либо задайте прокси, как выше.

Из **основного** сканирования убраны находки класса «инфо» (низкая значимость:
заголовки сервера, информационные признаки). В основном скане фиксируются

В **расширенном** скане фиксацию инфо-находок можно включить галочкой

### 3. Переработанная проверка уязвимостей + CVE

**3а. Качество находок (борьба с ложными срабатываниями).**
Правила (`scanner/vuln_rules.py`) и сбор наблюдений (`scanner/webscan.py`)
переписаны:

- **Контентная валидация.** Находка подтверждается сигнатурой в

- **Адекватный severity с обоснованием.** У каждой находки есть поле
  `severity_reason` — почему это critical/warning/info (например,

  компрометация → warning»). Отображается в отчёте.
- **Полные URL и атрибуция инструмента.** Каждая находка показывает
  полный URL и помечена инструментом (`[curl]`, `[whatweb]`,
  `[nmap]`, `[nikto]` и т.д.).
- **Дедупликация.** Одинаковые находки (один и тот же URL от
  разных инструментов) схлопываются в одну.

**3б. CVE — связь находок с известными уязвимостями.**
Модуль `scanner/cve_lookup.py` сопоставляет обнаруженные версии

1. **Офлайн-таблица** сигнатур (`OFFLINE_SIGNATURES`) — работает без

   2.4.49/2.4.50 — CVE-2021-41773/42013).
2. **Онлайн-запрос к NVD/OSV API** по версии продукта.
3. **nmap NSE `vulners`** — скрипт сопоставления баннеров с базой
   vulners.

> **Важно (изменение по требованию).** Онлайн-запрос к NVD/OSV и
> nmap NSE `vulners` включены **по умолчанию в ОСНОВНОМ скане**
> (фиксированный пресет). В **расширенном скане** это отдельные
> галочки («CVE: онлайн NVD/OSV», «CVE: nmap vulners»), обе включены
> по умолчанию. Онлайн-запросы опциональны и деградируют
> аккуратно: нет сети — остаётся офлайн-таблица.
>
> Флаги CLI: `--cve-online`/`--no-cve-online`, `--vulners`/`--no-vulners`.

В столбце «Уязвимости» появился блок CVE: идентификатор (ссылка на

## Два класса сканирования

Каждый запуск принадлежит одному из двух **классов**, статистика и «Отличия»
ведутся **раздельно по классу** (сравнение идёт только с прошлыми запусками
того же класса):

| Класс | Кнопка / CLI | Параметры |
|-------|--------------|-----------|
| **основное** | «Основной скан» / `./netinv scan --main` | Фиксированный пресет: обход SYN-защиты (`-sT`), профиль `balanced`, расширенные NSE, web-фингерпринт, `alive_no_ports advanced check`, **обратный DNS (`dig -x`)**. Параметры не выбираются. |
| **расширенное** | «Расширенный скан (настраиваемый)» / `./netinv scan` | Все параметры выбираются вручную: режим SYN, профиль, порты, NSE, web, `alive_no_ports`, **обратный DNS (`dig -x`)**. |

В **истории запусков** для каждого прогона показывается класс
(основное/расширенное), а для расширенного — краткие опции (обход SYN-защиты,
профиль, порты, NSE, web, alive_no_ports, `dig -x`).

> В основном скане углублённая проверка `alive_no_ports` ограничена top-3000
> TCP-портов (вместо полного `-p-`), чтобы фиксированный пресет не растягивался
> на часы. В расширенном скане при включённой галочке используется полный `-p-`.

## Обратный DNS (`dig -x`) — поле «Доменное имя»

Для каждого найденного IP выполняется обратное разрешение имени
командой `dig -x <IP> +short` (PTR-запись). Результат записывается в
поле отчёта **«Доменное имя»**.

- **Основной скан** — обратный DNS выполняется **всегда** (часть
  фиксированного пресета).
- **Расширенный скан** — включается опцией: галочка «обратный DNS
  (dig -x)» в форме или флаг `--dig-rdns` в CLI.

Логика заполнения имени: PTR-имя от `dig` имеет приоритет над hostname,
полученным от nmap; если `dig` ничего не вернул (нет PTR / недоступен /
таймаут) — остаётся имя от nmap, иначе «—». Таймаут одного запроса
ограничен (`+time=8 +tries=1`), поэтому отсутствие DNS не затягивает скан.

> Требуется утилита `dig` (пакет `dnsutils` / `bind-utils`). Если её нет в
> системе, поле «Доменное имя» заполняется только из nmap, скан не
> прерывается.

## Привязка доменов к объекту и разведка поддоменов

К объекту сканирования можно привязать не только диапазон IP-адресов
(CIDR), но и **один или несколько доменов**. IP-диапазон остаётся
**обязательным** — объект нельзя создать только из доменов; домены
добавляются как **дополнительный** источник целей и обогащают итоговую
таблицу новыми хостами и их доменными именами.

### Как обрабатываются домены

Уровень домена определяется по числу меток (частей, разделённых точкой):

| Тип домена | Пример | Действие NetInv |
|------------|--------|-----------------|
| **Домен 2-го уровня (apex)** | `domainname.ru` | Сначала **поиск поддоменов** утилитами `dnsmap`, `dnsenum`, `dnsrecon`, затем резолв IP найденных поддоменов и самого домена. |
| **Домен 3-го и ниже уровней** | `domain1.domainname.ru` | Просто **резолв IP-адреса** (`dig +short A`, при отсутствии `dig` — системный резолвер) и добавление его к сканированию. |

Все полученные IP-адреса (из CIDR, из резолва доменов и из найденных
поддоменов) объединяются в один список целей и передаются `nmap` единым
запуском. Дубликаты исключаются.

### Колонка «Источник» в отчёте

Каждый IP в итоговой таблице помечается источником, из которого он попал
в скан:

| Источник | Значение |
|----------|----------|
| **CIDR** | IP попал из обязательного диапазона объекта |
| **домен** | IP получен прямым резолвом привязанного домена |
| **поддомен** | IP получен из поддомена, найденного при разведке |

Для источников «домен» и «поддомен» рядом показывается, какой именно
домен дал этот IP. Доменное имя из прямой разведки (forward DNS) также
используется для заполнения поля **«Доменное имя»**, если обратный
`dig -x` ничего не вернул.

### Секция «Поддомены» в отчёте

Под основной таблицей выводится отдельная таблица **«🔎 Поддомены»** со
всеми поддоменами, обнаруженными при последней разведке: родительский
домен, поддомен, его IP, утилита-источник (`dnsmap`/`dnsenum`/`dnsrecon`)
и дата находки.

### Режим brute-force

Разведка поддоменов имеет два режима:

- **Быстрый (по умолчанию)** — пассивный/словарный режим утилит без
  тяжёлого перебора. Применяется всегда, когда к объекту привязан
  apex-домен.
- **Brute-force** — включается **галочкой «Brute-force поддоменов»** в
  форме расширенного скана или флагом `--dns-brute` в CLI. Включает
  перебор по словарю утилит (дольше, но полнее). Таймаут разведки в этом
  режиме увеличен.

> Утилиты `dnsmap`, `dnsenum`, `dnsrecon` — **необязательные**. Если они
> не установлены, разведка поддоменов пропускается с предупреждением в
> логе, а резолв привязанных доменов и сам скан продолжаются. Инсталлятор
> ставит их отдельно и не прерывает установку, если пакет недоступен в
> репозитории.

## Деление отчёта на «живые» и «возможные артефакты Palo Alto»

Отчёт делится на две секции:

1. **✅ Гарантированно «живые» хосты** — узлы хотя бы с одним подтверждённым
   сервисом (полное TCP-рукопожатие `-sT` + подтверждённый сервис,
   `confidence=confirmed`).
2. **⚠ Возможные артефакты защиты Palo Alto** — узлы без подтверждённых
   сервисов: только `syncookie_suspect`-порты, `alive_no_ports` либо пропавшие
   IP. Может генерироваться SYN-cookie proxy на Palo Alto — требует ручной
   верификации.

## Подсветка изменений (требования 5–8)

В web-отчёте изменения относительно предыдущего запуска того же класса
выделяются цветом, а в колонке «Отличия от предыдущего» — текстом на русском:

| Ситуация | Подсветка | Текст в «Отличиях» |
|----------|-----------|--------------------|
| Новый IP (не было в прошлом запуске) | строка/бейдж IP — зелёным | «Обнаружен новый IP» |
| IP пропал (был в прошлом, нет сейчас) | строка/бейдж IP — красным | «IP не найден» |
| Новые порты/сервисы | порт — зелёным | «Обнаружены новые порты <список>» / «Обнаружены новые сервисы <список>» |
| Пропавшие порты/сервисы | — | «Порты <список> не обнаружены» / «Сервисы <список> не обнаружены» |

## Учёт защиты Palo Alto (SYN Flood protection + SYN Cookies)

Когда на Palo Alto включена защита от SYN Flood в режиме **SYN Cookies**,
firewall сам отвечает `SYN-ACK` на входящие `SYN` **до** реального установления
соединения с защищаемым хостом. Из-за этого классический SYN-скан (`nmap -sS`)
видит «open» даже там, где порт закрыт, — ложные срабатывания (артефакты
SYN-proxy).

Решение в NetInv:

1. **Основной метод — TCP Connect (`nmap -sT`)**: полное трёхстороннее
   рукопожатие. Порт считается реально открытым, только когда handshake
   завершает конечный хост, а не firewall.
2. **Контроль скорости/таймингов** (профили) — чтобы не превышать пороги зон
   защиты SYN Flood (alarm/activate/maximal rate):
   - `stealth` — `-T2`, min-rate 50 / max-rate 150, scan-delay 20ms (рекомендуется для боевого периметра за Palo Alto);
   - `balanced` — `-T3`, до 400 pps;
   - `fast` — `-T4` (только для доверенного сегмента без жёстких порогов).
3. **Сервисная верификация (`-sV` + NSE `banner`)** — подтверждает, что за
   портом живой сервис. Порт, открытый по `-sT`, но без подтверждённого
   сервиса, помечается `syncookie_suspect` — возможный артефакт SYN-cookie
   proxy, требует ручной проверки.

## Узлы `alive_no_ports` и углублённая проверка (advanced check)

Отдельный частый случай за Palo Alto: узел **отвечает на host discovery**
(пингуется/виден в фазе обнаружения), но в результатах **нет ни одного
открытого порта, сервиса и web-ресурса**. Такие узлы NetInv автоматически
помечает флагом **`alive_no_ports`** — в web-отчёте под IP появляется
бейдж `alive_no_ports`, а в CSV заполняется колонка «Статус узла».

Причины бывают разными: хост действительно «глухой» (все порты закрыты/
фильтруются), сканировались не те порты, мешает межсетевой экран, либо это
ещё один артефакт SYN-защиты. Чтобы разобраться, предусмотрена
необязательная **углублённая проверка**.

### Галочка «alive_no_ports advanced check»

В форме запуска скана (на главной странице у объекта и в шапке отчёта) есть
флажок **«alive_no_ports advanced check»**. Если он включён, то после
основного скана для **каждого** узла с флагом `alive_no_ports`
дополнительно выполняются три команды `nmap`:

1. `nmap -sT -Pn -p- --max-retries 2 --scan-delay 30ms <IP>`
   — полное TCP Connect-сканирование всех 65535 портов с щадящим темпом
   (учёт порогов SYN Flood). Цель — найти редкие/нестандартные открытые
   TCP-порты, пропущенные основным профилем.
2. `nmap -sT -Pn --reason -p 80,443,22,3389 <IP>`
   — прицельная проба ключевых портов с выводом **причины** состояния
   (`--reason`): `closed (reset)`, `filtered (no-response)` и т.п. Это
   помогает отличить «реально закрыто» (приходит RST от хоста) от
   «фильтруется/проксируется» (ответа нет — возможный SYN-cookie proxy).
3. `nmap -sU -Pn --top-ports 50 --reason -vv <IP>`
   — проверка 50 самых частых **UDP**-портов (DNS, SNMP, NTP и т.д.),
   которые TCP-скан не видит в принципе. Открытыми считаются **только**
   порты в состоянии `state=open` (состояния `open|filtered` к открытым
   не относятся — для UDP они означают «нет ответа», т.е. неопределённость).

По итогам формируется текстовое **пояснение** (на русском), которое
сохраняется к узлу и отображается:

- в web-отчёте — раскрывающийся блок **«advanced check»** под IP;
- в CSV — колонка **«alive_no_ports advanced check»**.

Пояснение начинается со строки `ВЫВОД:` с итоговой интерпретацией
(например: найдены нестандартные TCP-порты; обнаружены UDP-сервисы; все
порты закрыты — узел действительно «глухой»; ответов нет — вероятна
фильтрация/SYN-proxy и т.п.), за которой следуют детали по каждой из трёх
команд.

> Внимание: полное сканирование `-p-` по всем 65535 портам — операция
> небыстрая (особенно с щадящим `--scan-delay`). Углублённая проверка
> запускается только при явно включённой галочке и только для узлов
> `alive_no_ports`.

Из CLI тот же режим включается флагом **`--advanced-anp`**:

```bash
./netinv scan --advanced-anp
# или напрямую:
.venv/bin/python scanner/scanner.py <args> --advanced-anp
.venv/bin/python run_cron.py --advanced-anp
```

Аналогично обратный DNS в расширенном скане включается флагом
**`--dig-rdns`** (в основном скане он всегда включён):

```bash
./netinv scan --dig-rdns
# или напрямую:
.venv/bin/python scanner/scanner.py <args> --dig-rdns
.venv/bin/python run_cron.py --dig-rdns
# основной скан — dig -x выполняется автоматически:
.venv/bin/python run_cron.py --main
```

## Обновление до актуальной версии

Скрипт `update.sh` обновляет установку из **локального источника**
(архив `netinv.tar.gz` или распакованный каталог) — рассчитан на
оффлайн/изолированные среды Continuous Pentest без доступа в интернет.

```bash
cd /opt/netinv

# Автопоиск netinv.tar.gz рядом с проектом:
./netinv update

# Либо явно указать источник:
./netinv update /путь/к/netinv.tar.gz       # из архива
./netinv update /путь/к/netinv_new_dir       # из распакованного каталога
```

Что делает `update.sh` по шагам:

1. Определяет источник (аргумент или автопоиск `netinv.tar.gz`), проверяет
   целостность новой версии (наличие ключевых файлов).
2. Показывает переход версий (файл `VERSION`): текущая → новая.
3. Делает **резервную копию** текущего кода и `data/data.db` в
   `backups/<метка-времени>/` (для отката).
4. Обновляет файлы кода, **СОХРАНЯЯ `data/data.db` без изменений**
   (история сканов, пользователи, описания IP не теряются) и не трогая `.venv`.
5. Обновляет зависимости в существующем `.venv` (`requirements.txt`).
6. Применяет **миграции схемы** БД (`db.init_db()` — `ALTER TABLE ... IF NOT
   EXISTS`, без потери данных).

Опции:

```bash
./netinv update --yes          # без интерактивного подтверждения
./netinv update --no-deps      # не переустанавливать зависимости
./netinv update --no-backup    # без резервной копии (НЕ рекомендуется)
./netinv update --help         # полная справка
```

> **Откат.** Если что-то пошло не так, восстановите код из
> `backups/<метка>/code_prev.tar.gz` и БД из `backups/<метка>/data/data.db`.
>
> ```bash
> tar xzf backups/<метка>/code_prev.tar.gz -C /opt/netinv
> cp backups/<метка>/data/data.db /opt/netinv/data/data.db
> ```

> Скрипт никогда не перезаписывает базу `data/data.db` и не удаляет
> каталог `backups/`. Для применения устаревших/удалённых файлов
> используется `rsync` (если установлен); иначе — копирование поверх.

## Авторизация и группа cpt (требования 13–14)

Доступ к web-приложению разрешён **только локальным пользователям**,
входящим в группу **cpt** (Continuous Penetration Test):

- Пользователи хранятся в таблице `users` (хеш пароля — werkzeug PBKDF2-SHA256).
- Принадлежность к cpt внутри приложения эмулируется флагом `in_cpt`:
  вход разрешён только при `in_cpt=1`.
- На уровне ОС `install.sh` создаёт реальную группу `cpt`
  (`groupadd -f cpt`) для разграничения прав на файлы проекта.

### Создание пользователей

При установке (`./install.sh`) интерактивно предлагается создать первого
пользователя (без него вход невозможен). Позже пользователей можно
добавлять/обновлять командой:

```bash
./netinv adduser                 # интерактивно (имя + скрытый ввод пароля)
./netinv adduser alice           # имя задано, пароль спросит
# или напрямую:
.venv/bin/python scanner/manage_users.py add --batch   # цикл добавления
.venv/bin/python scanner/manage_users.py list          # список
.venv/bin/python scanner/manage_users.py del alice      # удалить
```

Неинтерактивная установка (без запроса пользователей): переменная
`NETINV_NONINTERACTIVE=1 ./install.sh` — в этом случае создайте
пользователя позже через `./netinv adduser`.

> Дополнительно рекомендуется задать секрет сессии Flask через
> переменную `NETINV_SECRET` (иначе используется временный). Для
> боевого использования дополнительно поднимайте приложение за
> reverse-proxy (nginx) с TLS либо ограничьте доступ по firewall/SSH-туннелю.

## Режимы по отношению к SYN-защите

Доступно два режима (выбираются в web-форме или флагом `--syn-mode`):

| Режим | Как сканирует | Назначение |
|-------|--------------|-----------|
| `evasion` (по умолч.) | TCP Connect `-sT`, TCP host discovery, тихий тайминг | **Обход** SYN Flood/SYN Cookies: достоверно работает сквозь SYN-cookie proxy, не триггерит пороги. Не требует root. |
| `direct` | SYN-скан `-sS`, ICMP echo discovery | **Без обхода**: обычный быстрый скан для доверенного сегмента без firewall. Требует root (raw-сокеты). |


Либо systemd timer (`/etc/systemd/system/netinv.service` + `netinv.timer`) — по
аналогии. При каждом запуске diff-движок автоматически пересчитывает отличия от
предыдущего и позапрошлого сканирования.

---

## Как считаются отличия

После каждого запуска для каждого IP пересчитывается строка состояния
**в рамках своего класса скана** (основное / расширенное):

- **первое обнаружение** — фиксируется один раз (отдельно по классу);
- **предыдущее** и **позапрошлое** — два последних завершённых запуска того же
  класса до текущего;
- отличия считаются по множествам портов и сервисов (требования 5–8):
  новые/пропавшие порты и сервисы, новые/пропавшие IP — см. раздел
  «Подсветка изменений». Дополнительно по web-ресурсам: `➕ добавлено`,
  `➖ удалено`, `✎ изменено` (например, смена версии сервиса).

### Экспорт в CSV

Кнопка **CSV** в отчёте выгружает файл с именем вида
**`scan_YYYY_MM_DD_TIME.csv`** (напр., `scan_2026_06_11_074401.csv`),
разделитель `;`, кодировка UTF-8. В экспорт входят колонка
«Описание», «Первое обнаружение» и русский текст «Отличий».

## Замечания по безопасности и эксплуатации

- БД — единый файл `data/data.db` (SQLite, WAL). Бэкап = копия файла.
- Для больших периметров и долгой истории профиль `stealth` снижает риск
  блокировок и срабатывания SYN-flood зон Palo Alto.
- `syncookie_suspect` в таблице — сигнал перепроверить порт вручную
  (`nmap -sT -sV -p <port> <ip>` напрямую / `ncat`), т.к. это может быть
  артефакт SYN-cookie proxy.
- Логи nmap по каждому запуску хранятся в поле `scan_runs.log`.

## Устранение неполадок

### `attempt to write a readonly database` при добавлении объекта (HTTP 500)

Причина: установка выполнялась от root (`sudo ./install.sh`), поэтому каталог
`data/` и файл `data/data.db` принадлежат root, а web-приложение запущен
от обычного пользователя. SQLite требует прав записи И на файл БД, И
на каталог (из-за режима WAL и журнала).

Решение (выполнить в каталоге проекта, например `/opt/netinv`):

```bash
sudo chown -R "$(id -un):$(id -gn)" /opt/netinv
```

Свежий `install.sh` делает это автоматически: при запуске через `sudo`
он возвращает владение каталога исходному пользователю (`$SUDO_USER`).
Рекомендация: устанавливать и запускать от одного и того же пользователя.

### `ReadTimeoutError` / таймаут pip при установке

Медленный доступ к `files.pythonhosted.org`. Свежий `install.sh` уже задаёт
`--timeout 120 --retries 10` и повторяет установку. Если сеть очень
нестабильна, просто запустите `./install.sh` повторно (уже скачанное
кэшируется) либо укажите зеркало:

```bash
.venv/bin/pip install --timeout 120 --retries 10 \
    -i https://pypi.org/simple -r requirements.txt
```
