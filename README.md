# NetInv — инвентаризационное сканирование подсети для Continuous Penetration Test

Комплект скриптов и web-приложения для периодического инвентаризационного
сканирования подсети организации с накоплением истории и выявлением отличий
между запусками. Рассчитан на запуск из **Kali Linux 2026.1** с использованием
предустановленных инструментов (`nmap`, `whatweb`, `curl`).

> Применяйте только в пределах сетей, которыми владеете или на сканирование
> которых имеете письменное разрешение. Инструмент предназначен для легального
> Continuous Penetration Test по своему периметру.

| Web-ресурсы | curl + whatweb (код ответа, Server, title, технологии) |

> не к конкретному запуску, поэтому описание сохраняется между сканированиями.

## Новое в версии 1.3.0

1. **Сортировка доменов по уровням.** Привязанные домены и найденные
   поддомены сортируются сначала по доменам первого уровня (`.com`, `.org`,
   `.ru`), затем второго (`coffee.ru`, `gravity.ru`, `zoon.ru`), затем третьего
   (`alive.ya.ru`, `crimson.ya.ru`, `people.ya.ru`) и так далее. Ключ сортировки —
   `(число меток, метки в обратном порядке)` (`scanner/db.py::domain_sort_key`).

2. **Настраиваемая ширина колонок.** Ширину любой колонки отчёта можно
   менять перетягиванием за правый край заголовка. Ширины сохраняются в
   `localStorage` (по ключу таблицы). Горизонтальная прокрутка всегда видима.
   Двойной клик по ручке сбрасывает ширину (`webapp/static/table-resize.js`).

3. **Подгрузка результатов по клику на «Истории запусков».** Клик по
   строке истории подгружает (AJAX, `GET /run/<id>/rows`) таблицу результатов
   именно этого запуска (снимок, без сравнения с другими сканированиями).
   Активная строка подсвечивается.

4. **Колонки «Администраторы» и «Контроль и защита»** (после «Описания»).
   «Администраторы» — свободный редактируемый текст; «Контроль и защита» —
   набор галочек: **CPT**, **SOC**, **сканер уязвимостей**, **WAF**, **DDOS**.
   Оба поля хранятся в связке с IP (таблица `ip_attributes`), сохраняются
   через AJAX (`POST /attrs/<target_id>`) и попадают в CSV.

5. **Столбец «Уязвимости»** (после «Web-ресурсы»). Базовая, неинтрузивная
   проверка web-сервисов с подсветкой по критичности. Инструменты:
   `curl` (security-headers, открытые файлы/панели), `nmap` http-NSE, а при
   расширенном скане — `nikto`, `wpscan` (если определён WordPress), `dalfox`.
   Уровни критичности:
   - **critical** (красная подсветка строки, максимально оперативное реагирование):
     открытые служебные/админские панели и тестовые разделы; устаревшие
     версии веб-серверов/CMS/плагинов с известными RCE/SQLi/XSS
     (например, Apache 2.4.49/2.4.50 — CVE-2021-41773/42013); открытые
     конфигурационные/backup-файлы (`.git`, `.env`, `backup.sql`).
   - **warning** (жёлтая): отсутствие/неправильная настройка security-headers
     (HSTS, X-Frame-Options, CSP, X-Content-Type-Options).
   - **info** (синяя): прочие наблюдения.

   Классификатор находок — `scanner/vuln_rules.py` (не запускает инструменты,
   только разбирает наблюдения). Сбор наблюдений — `scanner/webscan.py`.

> **Безопасность и SYN-защита Palo Alto.** Проверки уязвимостей по умолчанию
> базовые и неинтрузивные (без активного brute-force/эксплуатации), чтобы не
> провоцировать пороги Palo Alto. Тяжёлые инструменты (nikto/wpscan/dalfox)
> запускаются только при расширенном скане.
>
> **Все инструменты опциональны.** Если nikto/wpscan/dalfox/dig не
> установлены, соответствующий шаг пропускается с предупреждением,
> сканирование не прерывается (graceful degradation).

## Два класса сканирования

Каждый запуск принадлежит одному из двух **классов**, статистика и «Отличия»
ведутся **раздельно по классу** (сравнение идёт только с прошлыми запусками
того же класса):

| Класс | Кнопка / CLI | Параметры |
|-------|--------------|-----------|
| **основное** | «Основной скан» / `./netinv scan --main` | Фиксированный пресет: обход SYN-защиты (`-sT`), профиль `balanced`, расширенные NSE, web-фингерпринт, `alive_no_ports advanced check`, **обратный DNS (`dig -x`)**. Параметры не выбираются. |
| **расширенное** | «Расширенный скан (настраиваемый)» / `./netinv scan` | Все параметры выбираются вручную: режим SYN, профиль, порты, NSE, web, `alive_no_ports`, **обратный DNS (`dig -x`)**. |

В **истории запусков** для каждого прогона показывается класс
(основное/расширенное), а для расширенного — краткие опции (обход SYN-защиты,
профиль, порты, NSE, web, alive_no_ports, `dig -x`).

> В основном скане углублённая проверка `alive_no_ports` ограничена top-3000
> TCP-портов (вместо полного `-p-`), чтобы фиксированный пресет не растягивался
> на часы. В расширенном скане при включённой галочке используется полный `-p-`.

## Обратный DNS (`dig -x`) — поле «Доменное имя»

Для каждого найденного IP выполняется обратное разрешение имени
командой `dig -x <IP> +short` (PTR-запись). Результат записывается в
поле отчёта **«Доменное имя»**.

- **Основной скан** — обратный DNS выполняется **всегда** (часть
  фиксированного пресета).
- **Расширенный скан** — включается опцией: галочка «обратный DNS
  (dig -x)» в форме или флаг `--dig-rdns` в CLI.

Логика заполнения имени: PTR-имя от `dig` имеет приоритет над hostname,
полученным от nmap; если `dig` ничего не вернул (нет PTR / недоступен /
таймаут) — остаётся имя от nmap, иначе «—». Таймаут одного запроса
ограничен (`+time=8 +tries=1`), поэтому отсутствие DNS не затягивает скан.

> Требуется утилита `dig` (пакет `dnsutils` / `bind-utils`). Если её нет в
> системе, поле «Доменное имя» заполняется только из nmap, скан не
> прерывается.

## Привязка доменов к объекту и разведка поддоменов

К объекту сканирования можно привязать не только диапазон IP-адресов
(CIDR), но и **один или несколько доменов**. IP-диапазон остаётся
**обязательным** — объект нельзя создать только из доменов; домены
добавляются как **дополнительный** источник целей и обогащают итоговую
таблицу новыми хостами и их доменными именами.

### Как обрабатываются домены

Уровень домена определяется по числу меток (частей, разделённых точкой):

| Тип домена | Пример | Действие NetInv |
|------------|--------|-----------------|
| **Домен 2-го уровня (apex)** | `domainname.ru` | Сначала **поиск поддоменов** утилитами `dnsmap`, `dnsenum`, `dnsrecon`, затем резолв IP найденных поддоменов и самого домена. |
| **Домен 3-го и ниже уровней** | `domain1.domainname.ru` | Просто **резолв IP-адреса** (`dig +short A`, при отсутствии `dig` — системный резолвер) и добавление его к сканированию. |

Все полученные IP-адреса (из CIDR, из резолва доменов и из найденных
поддоменов) объединяются в один список целей и передаются `nmap` единым
запуском. Дубликаты исключаются.

### Колонка «Источник» в отчёте

Каждый IP в итоговой таблице помечается источником, из которого он попал
в скан:

| Источник | Значение |
|----------|----------|
| **CIDR** | IP попал из обязательного диапазона объекта |
| **домен** | IP получен прямым резолвом привязанного домена |
| **поддомен** | IP получен из поддомена, найденного при разведке |

Для источников «домен» и «поддомен» рядом показывается, какой именно
домен дал этот IP. Доменное имя из прямой разведки (forward DNS) также
используется для заполнения поля **«Доменное имя»**, если обратный
`dig -x` ничего не вернул.

### Секция «Поддомены» в отчёте

Под основной таблицей выводится отдельная таблица **«🔎 Поддомены»** со
всеми поддоменами, обнаруженными при последней разведке: родительский
домен, поддомен, его IP, утилита-источник (`dnsmap`/`dnsenum`/`dnsrecon`)
и дата находки.

### Режим brute-force

Разведка поддоменов имеет два режима:

- **Быстрый (по умолчанию)** — пассивный/словарный режим утилит без
  тяжёлого перебора. Применяется всегда, когда к объекту привязан
  apex-домен.
- **Brute-force** — включается **галочкой «Brute-force поддоменов»** в
  форме расширенного скана или флагом `--dns-brute` в CLI. Включает
  перебор по словарю утилит (дольше, но полнее). Таймаут разведки в этом
  режиме увеличен.

> Утилиты `dnsmap`, `dnsenum`, `dnsrecon` — **необязательные**. Если они
> не установлены, разведка поддоменов пропускается с предупреждением в
> логе, а резолв привязанных доменов и сам скан продолжаются. Инсталлятор
> ставит их отдельно и не прерывает установку, если пакет недоступен в
> репозитории.

## Деление отчёта на «живые» и «возможные артефакты Palo Alto»

Отчёт делится на две секции:

1. **✅ Гарантированно «живые» хосты** — узлы хотя бы с одним подтверждённым
   сервисом (полное TCP-рукопожатие `-sT` + подтверждённый сервис,
   `confidence=confirmed`).
2. **⚠ Возможные артефакты защиты Palo Alto** — узлы без подтверждённых
   сервисов: только `syncookie_suspect`-порты, `alive_no_ports` либо пропавшие
   IP. Может генерироваться SYN-cookie proxy на Palo Alto — требует ручной
   верификации.

В web-отчёте изменения относительно предыдущего запуска того же класса
выделяются цветом, а в колонке «Отличия от предыдущего» — текстом на русском:

## Учёт защиты Palo Alto (SYN Flood protection + SYN Cookies)

Когда на Palo Alto включена защита от SYN Flood в режиме **SYN Cookies**,
firewall сам отвечает `SYN-ACK` на входящие `SYN` **до** реального установления
соединения с защищаемым хостом. Из-за этого классический SYN-скан (`nmap -sS`)
видит «open» даже там, где порт закрыт, — ложные срабатывания (артефакты
SYN-proxy).

Решение в NetInv:

1. **Основной метод — TCP Connect (`nmap -sT`)**: полное трёхстороннее
   рукопожатие. Порт считается реально открытым, только когда handshake
   завершает конечный хост, а не firewall.
2. **Контроль скорости/таймингов** (профили) — чтобы не превышать пороги зон
   защиты SYN Flood (alarm/activate/maximal rate):
   - `stealth` — `-T2`, min-rate 50 / max-rate 150, scan-delay 20ms (рекомендуется для боевого периметра за Palo Alto);
   - `balanced` — `-T3`, до 400 pps;
   - `fast` — `-T4` (только для доверенного сегмента без жёстких порогов).
3. **Сервисная верификация (`-sV` + NSE `banner`)** — подтверждает, что за
   портом живой сервис. Порт, открытый по `-sT`, но без подтверждённого
   сервиса, помечается `syncookie_suspect` — возможный артефакт SYN-cookie
   proxy, требует ручной проверки.

## Узлы `alive_no_ports` и углублённая проверка (advanced check)

Отдельный частый случай за Palo Alto: узел **отвечает на host discovery**
(пингуется/виден в фазе обнаружения), но в результатах **нет ни одного
открытого порта, сервиса и web-ресурса**. Такие узлы NetInv автоматически
помечает флагом **`alive_no_ports`** — в web-отчёте под IP появляется
бейдж `alive_no_ports`, а в CSV заполняется колонка «Статус узла».

Причины бывают разными: хост действительно «глухой» (все порты закрыты/
фильтруются), сканировались не те порты, мешает межсетевой экран, либо это
ещё один артефакт SYN-защиты. Чтобы разобраться, предусмотрена
необязательная **углублённая проверка**.

### Галочка «alive_no_ports advanced check»

В форме запуска скана (на главной странице у объекта и в шапке отчёта) есть
флажок **«alive_no_ports advanced check»**. Если он включён, то после
основного скана для **каждого** узла с флагом `alive_no_ports`
дополнительно выполняются три команды `nmap`:

1. `nmap -sT -Pn -p- --max-retries 2 --scan-delay 30ms <IP>`
   — полное TCP Connect-сканирование всех 65535 портов с щадящим темпом
   (учёт порогов SYN Flood). Цель — найти редкие/нестандартные открытые
   TCP-порты, пропущенные основным профилем.
2. `nmap -sT -Pn --reason -p 80,443,22,3389 <IP>`
   — прицельная проба ключевых портов с выводом **причины** состояния
   (`--reason`): `closed (reset)`, `filtered (no-response)` и т.п. Это
   помогает отличить «реально закрыто» (приходит RST от хоста) от
   «фильтруется/проксируется» (ответа нет — возможный SYN-cookie proxy).
3. `nmap -sU -Pn --top-ports 50 --reason -vv <IP>`
   — проверка 50 самых частых **UDP**-портов (DNS, SNMP, NTP и т.д.),
   которые TCP-скан не видит в принципе. Открытыми считаются **только**
   порты в состоянии `state=open` (состояния `open|filtered` к открытым
   не относятся — для UDP они означают «нет ответа», т.е. неопределённость).

По итогам формируется текстовое **пояснение** (на русском), которое
сохраняется к узлу и отображается:

- в web-отчёте — раскрывающийся блок **«advanced check»** под IP;
- в CSV — колонка **«alive_no_ports advanced check»**.

Пояснение начинается со строки `ВЫВОД:` с итоговой интерпретацией
(например: найдены нестандартные TCP-порты; обнаружены UDP-сервисы; все
порты закрыты — узел действительно «глухой»; ответов нет — вероятна
фильтрация/SYN-proxy и т.п.), за которой следуют детали по каждой из трёх
команд.

> Внимание: полное сканирование `-p-` по всем 65535 портам — операция
> небыстрая (особенно с щадящим `--scan-delay`). Углублённая проверка
> запускается только при явно включённой галочке и только для узлов
> `alive_no_ports`.

Из CLI тот же режим включается флагом **`--advanced-anp`**:

```bash
./netinv scan --advanced-anp
# или напрямую:
.venv/bin/python scanner/scanner.py <args> --advanced-anp
.venv/bin/python run_cron.py --advanced-anp
```

Аналогично обратный DNS в расширенном скане включается флагом
**`--dig-rdns`** (в основном скане он всегда включён):

```bash
./netinv scan --dig-rdns
# или напрямую:
.venv/bin/python scanner/scanner.py <args> --dig-rdns
.venv/bin/python run_cron.py --dig-rdns
# основной скан — dig -x выполняется автоматически:
.venv/bin/python run_cron.py --main
```

## Быстрый старт (автоматическая установка)

Инсталлятор рассчитан на любые **Debian-совместимые** системы (Kali, Ubuntu,
Debian, Parrot). Он сам ставит **обязательные** системные пакеты (`nmap`,
`whatweb`, `curl`, `dnsutils`, `python3-venv`), создаёт виртуальное
окружение, ставит зависимости и инициализирует БД. Дополнительно пытается
установить **необязательные** утилиты разведки поддоменов (`dnsmap`,
`dnsenum`, `dnsrecon`) — если какого-то пакета нет в репозитории,
установка не прерывается.

```bash
# 1. Распаковать
sudo mkdir -p /opt/netinv && sudo tar xzf netinv.tar.gz -C /opt/netinv --strip-components=1
cd /opt/netinv

# 2. Установить всё одной командой (sudo нужен для apt-get)
sudo ./install.sh
```

## Обновление до актуальной версии

Скрипт `update.sh` обновляет установку из **локального источника**
(архив `netinv.tar.gz` или распакованный каталог) — рассчитан на
оффлайн/изолированные среды Continuous Pentest без доступа в интернет.

```bash
cd /opt/netinv

# Автопоиск netinv.tar.gz рядом с проектом:
./netinv update

# Либо явно указать источник:
./netinv update /путь/к/netinv.tar.gz       # из архива
./netinv update /путь/к/netinv_new_dir       # из распакованного каталога
```

Что делает `update.sh` по шагам:

1. Определяет источник (аргумент или автопоиск `netinv.tar.gz`), проверяет
   целостность новой версии (наличие ключевых файлов).
2. Показывает переход версий (файл `VERSION`): текущая → новая.
3. Делает **резервную копию** текущего кода и `data/data.db` в
   `backups/<метка-времени>/` (для отката).
4. Обновляет файлы кода, **СОХРАНЯЯ `data/data.db` без изменений**
   (история сканов, пользователи, описания IP не теряются) и не трогая `.venv`.
5. Обновляет зависимости в существующем `.venv` (`requirements.txt`).
6. Применяет **миграции схемы** БД (`db.init_db()` — `ALTER TABLE ... IF NOT
   EXISTS`, без потери данных).

Опции:

```bash
./netinv update --yes          # без интерактивного подтверждения
./netinv update --no-deps      # не переустанавливать зависимости
./netinv update --no-backup    # без резервной копии (НЕ рекомендуется)
./netinv update --help         # полная справка
```

> **Откат.** Если что-то пошло не так, восстановите код из
> `backups/<метка>/code_prev.tar.gz` и БД из `backups/<метка>/data/data.db`.
>
> ```bash
> tar xzf backups/<метка>/code_prev.tar.gz -C /opt/netinv
> cp backups/<метка>/data/data.db /opt/netinv/data/data.db
> ```

> Скрипт никогда не перезаписывает базу `data/data.db` и не удаляет
> каталог `backups/`. Для применения устаревших/удалённых файлов
> используется `rsync` (если установлен); иначе — копирование поверх.

## Запуск всей системы одной командой

```bash
./netinv                              # web-приложение на http://127.0.0.1:5000
./netinv web --host 0.0.0.0 --port 8080   # доступ в LAN (осторожно!)
```

При первом запуске, если окружение `.venv` отсутствует, `./netinv`
автоматически вызовет `install.sh` (bootstrap) — установка и запуск фактически
сводятся к одной команде `./netinv`.

Откройте `http://127.0.0.1:5000`:

- **Объекты** — добавить подсеть/хост (CIDR), выбрать **режим обхода SYN-защиты**
  и профиль таймингов, запустить скан.
- **Отчёт по объекту** — итоговая таблица (узлы отсортированы по возрастанию IP),
  история и отличия, экспорт в CSV.
- **История запусков** — все прогоны с фактической командой nmap и меткой
  профиль/режим (напр. `stealth/evasion`).

Сканирование запускается в фоне; обновите страницу отчёта через некоторое время.

> Режим `direct` использует SYN-скан (`nmap -sS`) и требует root
> (`sudo ./netinv ...` или запуск web-приложения от root). Режим `evasion`
> (по умолчанию) работает без root.

## Авторизация и группа cpt (требования 13–14)

Доступ к web-приложению разрешён **только локальным пользователям**,
входящим в группу **cpt** (Continuous Penetration Test):

- Пользователи хранятся в таблице `users` (хеш пароля — werkzeug PBKDF2-SHA256).
- Принадлежность к cpt внутри приложения эмулируется флагом `in_cpt`:
  вход разрешён только при `in_cpt=1`.
- На уровне ОС `install.sh` создаёт реальную группу `cpt`
  (`groupadd -f cpt`) для разграничения прав на файлы проекта.

### Создание пользователей

При установке (`./install.sh`) интерактивно предлагается создать первого
пользователя (без него вход невозможен). Позже пользователей можно
добавлять/обновлять командой:

```bash
./netinv adduser                 # интерактивно (имя + скрытый ввод пароля)
./netinv adduser alice           # имя задано, пароль спросит
# или напрямую:
.venv/bin/python scanner/manage_users.py add --batch   # цикл добавления
.venv/bin/python scanner/manage_users.py list          # список
.venv/bin/python scanner/manage_users.py del alice      # удалить
```

Неинтерактивная установка (без запроса пользователей): переменная
`NETINV_NONINTERACTIVE=1 ./install.sh` — в этом случае создайте
пользователя позже через `./netinv adduser`.

> Дополнительно рекомендуется задать секрет сессии Flask через
> переменную `NETINV_SECRET` (иначе используется временный). Для
> боевого использования дополнительно поднимайте приложение за
> reverse-proxy (nginx) с TLS либо ограничьте доступ по firewall/SSH-туннелю.

## Режимы по отношению к SYN-защите

Доступно два режима (выбираются в web-форме или флагом `--syn-mode`):

| Режим | Как сканирует | Назначение |
|-------|--------------|-----------|
| `evasion` (по умолч.) | TCP Connect `-sT`, TCP host discovery, тихий тайминг | **Обход** SYN Flood/SYN Cookies: достоверно работает сквозь SYN-cookie proxy, не триггерит пороги. Не требует root. |
| `direct` | SYN-скан `-sS`, ICMP echo discovery | **Без обхода**: обычный быстрый скан для доверенного сегмента без firewall. Требует root (raw-сокеты). |

## Запуск из CLI (без web)

```bash
# Добавить объект
python3 scanner/scanner.py --add-target "DMZ-филиал" "192.168.10.0/24"

# Список объектов
python3 scanner/scanner.py --list-targets

# Привязать домен(ы) к объекту (дополнительно к обязательному CIDR) —
# через web-интерфейс (кнопка «+ домен» у объекта).
# apex-домен (domainname.ru) — разведка поддоменов; домен 3+ уровня — только резолв.

# Запустить скан в режиме обхода SYN-защиты (по умолч.)
python3 scanner/scanner.py --target-id 1 --profile stealth

# Без обхода (SYN-скан, нужен root)
sudo python3 scanner/scanner.py --target-id 1 --syn-mode direct

# Проверить команду без запуска
python3 scanner/scanner.py --target-id 1 --dry-run

# Полный диапазон портов + расширенные NSE
python3 scanner/scanner.py --target-id 1 --full-ports --extra-nse

# Разведка поддоменов в режиме brute-force (дольше, но полнее)
python3 scanner/scanner.py --target-id 1 --dns-brute
```

Или через единую команду (прогон всех объектов):

```bash
./netinv scan --main                # ОСНОВНОЙ скан (фиксированный пресет, scan_class=main)
./netinv scan                       # РАСШИРЕННЫЙ, обход SYN-защиты
sudo ./netinv scan --syn-mode direct  # расширенный, без обхода
```

## Continuous Penetration Test (периодический запуск)

`run_cron.py` прогоняет все активные объекты и накапливает историю/отличия.

```bash
# Разовый прогон всех объектов в режиме обхода SYN-защиты (по умолч.)
python3 run_cron.py --profile stealth
# то же самое единой командой
./netinv scan --profile stealth

# Без обхода (SYN-скан, нужен root)
sudo python3 run_cron.py --profile stealth --syn-mode direct
sudo ./netinv scan --profile stealth --syn-mode direct
```

Crontab (каждую ночь в 02:30, режим обхода SYN-защиты):

```cron
30 2 * * * cd /opt/netinv && /opt/netinv/.venv/bin/python3 run_cron.py --profile stealth --syn-mode evasion >> /var/log/netinv.log 2>&1
```

Либо systemd timer (`/etc/systemd/system/netinv.service` + `netinv.timer`) — по
аналогии. При каждом запуске diff-движок автоматически пересчитывает отличия от
предыдущего и позапрошлого сканирования.

## Как считаются отличия

После каждого запуска для каждого IP пересчитывается строка состояния
**в рамках своего класса скана** (основное / расширенное):

- **первое обнаружение** — фиксируется один раз (отдельно по классу);
- **предыдущее** и **позапрошлое** — два последних завершённых запуска того же
  класса до текущего;
- отличия считаются по множествам портов и сервисов (требования 5–8):
  новые/пропавшие порты и сервисы, новые/пропавшие IP — см. раздел
  «Подсветка изменений». Дополнительно по web-ресурсам: `➕ добавлено`,
  `➖ удалено`, `✎ изменено` (например, смена версии сервиса).

### Экспорт в CSV

Кнопка **CSV** в отчёте выгружает файл с именем вида
**`scan_YYYY_MM_DD_TIME.csv`** (напр., `scan_2026_06_11_074401.csv`),
разделитель `;`, кодировка UTF-8. В экспорт входят колонка
«Описание», «Первое обнаружение» и русский текст «Отличий».

## Замечания по безопасности и эксплуатации

- БД — единый файл `data/data.db` (SQLite, WAL). Бэкап = копия файла.
- Для больших периметров и долгой истории профиль `stealth` снижает риск
  блокировок и срабатывания SYN-flood зон Palo Alto.
- `syncookie_suspect` в таблице — сигнал перепроверить порт вручную
  (`nmap -sT -sV -p <port> <ip>` напрямую / `ncat`), т.к. это может быть
  артефакт SYN-cookie proxy.
- Логи nmap по каждому запуску хранятся в поле `scan_runs.log`.

## Устранение неполадок

### `attempt to write a readonly database` при добавлении объекта (HTTP 500)

Причина: установка выполнялась от root (`sudo ./install.sh`), поэтому каталог
`data/` и файл `data/data.db` принадлежат root, а web-приложение запущен
от обычного пользователя. SQLite требует прав записи И на файл БД, И
на каталог (из-за режима WAL и журнала).

Решение (выполнить в каталоге проекта, например `/opt/netinv`):

```bash
sudo chown -R "$(id -un):$(id -gn)" /opt/netinv
```

Свежий `install.sh` делает это автоматически: при запуске через `sudo`
он возвращает владение каталога исходному пользователю (`$SUDO_USER`).
Рекомендация: устанавливать и запускать от одного и того же пользователя.

### `ReadTimeoutError` / таймаут pip при установке

Медленный доступ к `files.pythonhosted.org`. Свежий `install.sh` уже задаёт
`--timeout 120 --retries 10` и повторяет установку. Если сеть очень
нестабильна, просто запустите `./install.sh` повторно (уже скачанное
кэшируется) либо укажите зеркало:

```bash
.venv/bin/pip install --timeout 120 --retries 10 \
    -i https://pypi.org/simple -r requirements.txt
```
